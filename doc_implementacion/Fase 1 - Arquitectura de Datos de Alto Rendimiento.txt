Fase 1: Diseño de Arquitectura - Proyecto Integrador M4 (Versión Extendida)
Como Senior Data Engineer con visión estratégica, he diseñado esta arquitectura buscando el equilibrio óptimo entre costo-eficiencia (maximizando el AWS Free Tier) y potencia industrial (utilizando el stack de Spark + Kafka). Esta solución implementa un patrón Lambda integrado sobre una estructura de Medallion Architecture, garantizando la integridad de los datos históricos y la agilidad de los datos en tiempo real.
1. El Paradigma de la Arquitectura Medallion
La elección de una arquitectura de medallas (Bronze, Silver, Gold) no es estética, es una decisión de Gobernanza de Datos. Al desacoplar la ingesta de la transformación y el consumo, creamos un sistema donde cada capa tiene una responsabilidad única:
* Resiliencia: Si una regla de negocio en la capa Gold falla, podemos re-procesar todo desde la capa Bronze sin volver a extraer datos del origen.
* Escalabilidad: Permite que diferentes equipos (Analistas, Data Scientists, BI) consuman datos en diferentes estados de madurez.

Versión Descriptiva del Diagrama (Lectura para IA / Semántica)
Para asegurar la correcta interpretación del flujo de datos, a continuación se describe secuencialmente la topología de la arquitectura:
1. Flujo Batch (Histórico):
   * Origen: Base de datos PostgreSQL (datos transaccionales) y una API Pública (archivos JSON de clima/geografía).
   * Ingesta: Airbyte se conecta a ambas fuentes y extrae los datos de forma programada.
   * Aterrizaje (Raw): Airbyte deposita los datos crudos en Amazon S3 bajo las rutas /raw/postgres/ y /raw/api/.
2. Flujo Streaming (Tiempo Real):
   * Origen: Productores de eventos (simulación de telemetría o clickstream).
   * Ingesta: Apache Kafka actúa como broker o bus de mensajes recibiendo los eventos en tiempo real.
   * Aterrizaje/Consumo: Los eventos van a una Landing Zone en S3 (/raw/streaming/) o son leídos directamente en memoria por Spark.
3. Procesamiento (El Motor):
   * Se utiliza PySpark (ejecutado en clústeres efímeros de Databricks, AWS EMR o Glue para no saturar la orquestación).
   * Spark lee los datos Batch de la capa Raw y consume los datos de Kafka vía Spark Structured Streaming.
   * Spark limpia y estandariza los datos, guardándolos en la Capa Silver (Tablas Limpias en formato Parquet).
4. Capa Analítica y Consumo (Serving):
   * Spark realiza los cruces finales (JOINs entre histórico y streaming) y guarda el resultado consolidado en la Capa Gold.
   * Amazon Athena se conecta a S3 para permitir consultas SQL Ad-Hoc directamente sobre la capa Gold.
   * Amazon QuickSight lee de Athena/Gold para renderizar los dashboards visuales de negocio.
5. Orquestación y DevOps (El Cerebro):
   * Una instancia AWS EC2 (t2.micro) aloja Apache Airflow (desplegado en Docker).
   * Airflow no procesa datos; su única función es coordinar: le avisa a Airbyte cuándo extraer y a Spark cuándo procesar.
   * GitHub Actions provee integración continua (CI/CD), automatizando el testeo y subida de los archivos DAG hacia la instancia EC2.
3. Inmersión Profunda en las Capas del Data Lake
A. Capa Raw (Bronze) - La Fuente de la Verdad
* Estado: Datos inmutables ("as-is"). Está terminantemente prohibido modificar los archivos una vez depositados.
* Estructura de Directorios: Implementamos un particionamiento por fecha de ingesta: s3://.../raw/source/year=YYYY/month=MM/day=DD/hour=HH/.
* Importancia: Esta estructura permite el Backfilling. Si descubrimos un error en el código de Spark dos meses después, podemos volver a correr el proceso solo para los días afectados, ahorrando costos de cómputo.
B. Capa Silver (Processed) - Calidad e Integridad
* Estado: Datos tipados y normalizados. Aquí aplicamos el Schema Enforcement.
* Transformaciones Críticas: * Conversión de tipos (Strings a Integers/Decimals).
   * Estandarización de fechas (ISO-8601).
   * Manejo de Nulos (Imputación o descarte según la regla de negocio).
   * Deduplicación basada en llaves primarias de negocio.
* Formato Parquet: Usamos Parquet por su almacenamiento columnar. Esto permite a Amazon Athena leer solo las columnas necesarias (columnar pruning), reduciendo el costo por consulta en un 90% comparado con JSON.
C. Capa Gold (Curated/Analytical) - El Valor de Negocio
* Estado: Tablas de Hechos (Facts) y Dimensiones (Dimensions) optimizadas para el usuario final.
* Lógica de Negocio: Aquí es donde cruzamos la data histórica de Postgres con los eventos de Kafka.
* Particionamiento Estratégico: Basado en las "Preguntas Guía", particionamos por region y periodo. Esto asegura que un reporte de "Ventas Mensuales" solo escanee la data de ese mes específico.
4. Arquitectura Lambda: Fusión Batch y Streaming
Nuestro diseño resuelve el dilema de "Velocidad vs. Precisión":
1. Batch Layer (Alta Precisión): Airbyte e ingestas diarias de Postgres aseguran que los reportes históricos sean 100% exactos.
2. Speed Layer (Baja Latencia): Spark Structured Streaming consume de Kafka para capturar tendencias en minutos.
3. Serving Layer (Athena): Proporciona una vista unificada donde el usuario no nota si el dato vino de un proceso de ayer o de un evento de hace 5 minutos.
5. Decisiones Técnicas: Justificación y Alternativas
| Componente | Decisión | Justificación Senior | Alternativas Descartadas |
| Orquestación | Airflow (EC2) | Permite programar dependencias complejas y reintentos automáticos. Vital para el control de errores. | AWS Step Functions (menos flexible para herramientas externas como Airbyte). |
| Cómputo | Spark Externo | Delegar a Databricks/EMR protege la memoria de la EC2, evitando reinicios de sistema inesperados. | Spark Local (Riesgo crítico de OOM en instancias t2.micro). |
| Formato | Parquet + Snappy | El mejor balance entre velocidad de compresión y eficiencia de lectura. | CSV/Avro (CSV es lento; Avro es mejor para escritura pero peor para analítica). |
| Ingesta | Airbyte | Democratiza la extracción de datos con conectores pre-construidos, reduciendo el código boilerplate. | Python scripts manuales (difíciles de mantener y escalar). |
6. Seguridad, Gobernanza y Observabilidad
Seguridad Proactiva
* IAM Roles: No usaremos llaves estáticas (AKIA...). La instancia EC2 asumirá un rol con permisos de escritura específicos en S3 mediante políticas de confianza.
* Cifrado: Todos los datos en S3 se cifrarán en reposo usando AES-256.
Observabilidad (Monitoring)
* Airflow Logs: Cada tarea enviará sus logs a una carpeta persistente para auditoría.
* Spark UI: Monitoreo de Shuffles y Data Skew (desequilibrio de datos) durante las transformaciones pesadas.
* Data Quality: Implementaremos validaciones básicas (Count checks) para asegurar que la cantidad de registros que salen de Raw coincidan con los que entran a Silver.
7. ⚠️ Gestión de Riesgos y Mitigación
1. Límites del Free Tier: El almacenamiento en S3 y las horas de EC2 son limitadas.
   * Mitigación: Implementaremos políticas de ciclo de vida (S3 Lifecycle Policies) para mover o borrar data experimental después de 7 días.
2. Consistencia Eventual: AWS S3 es consistente de forma eventual para escrituras.
   * Mitigación: Aseguraremos que Spark utilice el S3A Committer para evitar archivos corruptos o incompletos durante el guardado.
3. Idempotencia: Un fallo en el DAG podría causar duplicados si se corre dos veces.
   * Mitigación: Todos nuestros scripts de Spark usarán el modo overwrite con particionamiento dinámico para asegurar que re-correr una tarea no duplique registros.
Conclusión de la Fase 1: Esta arquitectura no solo cumple con las consignas, sino que establece un estándar de ingeniería de datos profesional, preparada para crecer y escalar bajo los principios de la arquitectura Medallion y Lambda.
