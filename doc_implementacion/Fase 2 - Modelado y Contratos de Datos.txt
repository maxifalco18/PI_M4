Fase 2: Modelado, Esquemas y Contratos de Datos - Proyecto Integrador M4
Como Senior Data Engineer, mi objetivo en esta fase es proteger la integridad del Data Lake. En arquitecturas distribuidas (Spark + S3), los errores de esquema no son simples warnings; causan fallos catastróficos o, peor aún, corrupción silenciosa de datos. Para evitarlo, implementaremos Contratos de Datos estrictos y un modelado basado en la evolución por capas (Medallion).
1. Contratos de Datos por Fuente (Data Contracts)
Antes de escribir el código de Spark, definimos las expectativas de entrada. Cualquier dato que no cumpla con este contrato será segregado en la capa Silver.
A. Fuente 1: API Pública (Clima/Geografía)
* Origen: Archivos JSON (ej. Patagonia_-41.json, Riohacha_11_538415.json).
* Naturaleza: Semi-estructurada, anidada.
* Contrato Esperado:
   * location_name (String): No nulo.
   * latitude (Double) / longitude (Double): Validado en rango geográfico válido (-90 a 90, -180 a 180).
   * metrics (Struct/Array): Objetos anidados que deberán ser aplanados (flattened).
* Frecuencia: Batch diario (Manual vía Airbyte).
B. Fuente 2: Base de Datos Relacional (PostgreSQL)
* Origen: Tablas transaccionales (ej. clientes, ventas o sucursales).
* Naturaleza: Estructurada (Esquema rígido).
* Contrato Esperado:
   * id_primario (Integer/UUID): Clave única, no nula (Primary Key).
   * updated_at (Timestamp): Obligatorio para permitir la carga incremental (High-Water Mark) en Airbyte.
* Frecuencia: Full Load inicial, luego Incremental Deduped.
C. Fuente 3: Streaming de Eventos (Apache Kafka)
* Origen: Tópicos de Kafka (ej. telemetria_eventos o clickstream).
* Naturaleza: Mensajería en tiempo real. Formato JSON.
* Contrato Esperado:
   * event_id (String/UUID): Para deduplicación exacta.
   * event_timestamp (Timestamp): Vital para el Watermarking en Spark Streaming (manejo de datos atrasados).
   * payload (JSON String): Contenido del evento.
2. Evolución del Modelo de Datos (Medallion)
Capa Bronze (Raw) - Schema-on-Read
* Estrategia: Ingesta ciega. Guardamos los datos exactamente como llegan de Airbyte y Kafka.
* Modelo: Archivos JSON/Parquet crudos particionados por año/mes/día.
* Regla de Oro: Cero transformaciones. Si un campo viene mal escrito desde el origen, se guarda mal escrito. Esto garantiza la auditabilidad forense.
Capa Silver (Processed) - Schema-on-Write & Enforcement
* Estrategia: Limpieza y tipado fuerte. Aquí Spark aplica el contrato de datos.
* Acciones de Modelado:
   1. Casting Explícito: col("latitude").cast(DoubleType()).
   2. Flattening: Extraer datos de los JSON anidados usando explode() o notación de punto (metrics.temperature).
   3. Deduplicación: Eliminar eventos de Kafka duplicados en una ventana de tiempo usando dropDuplicates(["event_id"]).
* Modelo Físico: Formato Parquet con compresión Snappy.
Capa Gold (Analytical) - Dimensional/OBT Modeling
* Estrategia: Optimizado para lectura en Amazon Athena y consumo visual (Quicksight).
* Paradigma Elegido: One Big Table (OBT) / Tabla Desnormalizada Ancha.
   * Justificación: Para entornos analíticos serverless como Athena, los JOINs masivos entre tablas de hechos y dimensiones son costosos computacionalmente. Cruzar la data en Spark y guardar una "Tabla Ancha" (OBT) reduce la latencia de las consultas de negocio a milisegundos.
* Columnas Clave para Particionamiento:
   * region (derivado de la API).
   * periodo (YYYY-MM derivado del Timestamp).
3. Gobernanza y Calidad de Datos (Data Quality)
Para que los datos sean confiables, el pipeline de Spark validará tres pilares de calidad antes de escribir en la capa Gold:
1. Completitud (Completeness): La columna id_primario y location_name deben tener una tasa de nulos del 0%.
2. Frescura (Freshness): Para el streaming, monitorearemos el retraso (lag) de los offsets en Kafka.
3. Unicidad (Uniqueness): No deben existir dos registros válidos para el mismo cliente en la misma marca de tiempo exacta.
4. ⚠️ RIESGOS TÉCNICOS Y MITIGACIONES
Riesgo 1: Schema Drift (Cambios de esquema en el origen)
Si la API pública cambia el nombre de la columna latitude a lat sin avisar, nuestro job de Spark fallará.
* Mitigación: En la lectura Silver, utilizaremos selección de columnas flexible o lectura con esquemas explícitos de PySpark (StructType). Si una columna esperada no viene, el script no fallará, sino que asignará NULL y levantará una alerta en Airflow.
Riesgo 2: Datos atrasados en Streaming (Late Data)
Un evento generado en un dispositivo a las 10:00 AM podría llegar a Kafka a las 10:05 AM por problemas de red.
* Mitigación: Implementaremos Watermarking en Spark Structured Streaming. Definiremos una ventana de tolerancia (ej. 10 minutos). Los datos que lleguen más tarde de ese umbral serán descartados o enviados a una tabla lateral para no afectar las agregaciones en tiempo real.
